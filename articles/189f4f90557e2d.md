個人開発でWebブラウザゲームを作る場合、技術構成を考えることは重要です。

AIエージェントの登場により、フルスタックのエンジニア以外でも、手軽に開発へトライしやすくなりました。  
一方で、実際に世の中に公開できる品質のものを作ろうとすると、考慮すべき点は多くあります。

特にマネタイズや中長期的な運用を検討している場合は、技術構成をしっかり考える必要があります。

技術検討をおろそかにしたまま本番稼働を迎えた場合、思わぬ不具合やトラブルにつながる恐れがあります。

## Webブラウザゲームの技術構成について

Webブラウザゲームを本番環境で稼働させるためには、ゲーム自体の設計や実装だけでなく、以下のような要素を考える必要があります。

- フロントエンド
- バックエンド
- データベース
- 認証
- ホスティング
- ドメイン
- 運用コスト
- 将来的な負荷

この記事では、個人開発でWebブラウザゲームを作る場合における、技術構成の考え方を備忘録として記載します。

## 前提

今回、想定しているのは、以下のようなWebブラウザゲームです。

- PC / スマホのブラウザで遊べる
- ログイン機能がある
- ユーザーデータを保存する
- ランキングやバトル結果を保存する
- 将来的に課金や広告も検討する
- 個人開発なので、運用コストは抑えたい

いわゆる静的サイトではなく、ユーザーごとの状態を持つWebアプリに近い構成です。

## 現在考えている構成

現時点では、以下のような構成を想定しています。

| 領域 | 使用サービス | 主な役割 |
| --- | --- | --- |
| フロントエンド | Cloudflare Pages | 画面・静的アセットの配信 |
| バックエンド | Render | APIサーバーの実行 |
| DB / Auth | Supabase | データベース・認証 |
| Domain / DNS | Cloudflare | ドメイン・DNS管理 |

ざっくり分けると、Cloudflare Pagesで画面を配信し、RenderでAPIサーバーを動かし、SupabaseでDBと認証を担当する構成です。

## フロントエンド：Cloudflare Pages

フロントエンドはCloudflare Pagesを使う想定です。

理由はシンプルで、静的フロントエンドの配信に向いていて、個人開発でも扱いやすいからです。

メリットは以下です。

- デプロイが簡単
- GitHub連携しやすい
- CDN配信される
- 小規模ならコストを抑えやすい
- 独自ドメインとの相性がよい

Webブラウザゲームの場合、画面表示や静的アセットの配信が多くなります。

そのため、フロントエンドを高速に配信できる環境を使うのは大事だと感じています。

## バックエンド：Render

バックエンドはRenderを想定しています。

APIサーバーを動かす場所として、個人開発では扱いやすい選択肢だと思います。

主な役割は以下です。

- バトル処理
- アイテム処理
- ランキング更新
- ユーザーごとの状態更新
- Supabaseとの接続

Webブラウザゲームに限らずですが、クライアント側だけで処理を完結させると改ざんリスクが高くなります。

そのため、重要な処理はバックエンド側で行う方が安全です。

例えば、以下のような処理です。

- 報酬付与
- 戦闘結果の確定
- アイテム消費
- 課金アイテムの反映

このような処理は、フロントエンドだけに任せない方がよいと考えています。

### Renderの無料枠を使う場合の注意点

RenderのFree Instanceを使う場合、一定時間アクセスがないとインスタンスがスリープします。

その後、次のアクセス時にインスタンスが起動するため、初回APIリクエストが遅くなる、いわゆるCold Startが発生します。

:::message alert
Webブラウザゲームでは、APIの初動が遅いとユーザー体験に直結します。  
本番運用を想定する場合は、有料プランを使うか、RenderによるCold Startの影響を許容できる設計にする必要があります。
:::

例えば、ゲーム開始時やバトル実行時のAPIが遅いと、ユーザーは「ゲームが止まった」と感じる可能性があります。

個人開発の検証段階では無料枠でもよいと思いますが、公開後に継続利用してもらうサービスとして考えるなら、バックエンドは有料プラン前提で考えた方が安全です。

## DB / Auth：Supabase

DBと認証はSupabaseを想定しています。

SupabaseはPostgreSQLをベースにしており、認証や管理画面も用意されています。

個人開発では、以下の点が便利です。

- PostgreSQLを使える
- Auth機能がある
- 管理画面からデータを確認しやすい
- API連携しやすい
- 小規模から始めやすい

Webブラウザゲームでは、ユーザーごとのデータが多くなります。

例えば、以下のようなデータです。

- ユーザー情報
- 所持キャラクター
- 所持アイテム
- 戦闘履歴
- ランキング
- メッセージ
- 課金状態

こうしたデータを扱う場合、最初からRDBで整理しておくと後から見通しがよくなります。

### Supabaseの無料枠を本番利用する場合の注意点

Supabaseは無料枠でも使い始めやすいですが、本番稼働では注意が必要です。

特に気にしたいのは以下です。

- 一定期間アクティビティがないとプロジェクトが一時停止する
- 無料枠にはデータベース容量やストレージ容量の上限がある
- 無料枠ではプロジェクト数にも制限がある
- 本番障害時の復旧やサポート面では有料プランの方が安心しやすい
- 成長後に無料枠の上限へ到達すると、移行や課金判断が必要になる

:::message alert
ゲームではユーザーデータが資産になります。  
本番公開後にSupabaseの無料枠を使い続ける場合は、停止・容量上限・バックアップ・復旧手順を事前に確認しておく必要があります。
:::

無料枠は、開発初期やMVP検証にはとても便利です。

一方で、ユーザーが継続して遊ぶブラウザゲームでは、データベースが止まることや、容量上限に気づかず運用することがリスクになります。

例えば、以下のようなデータは徐々に増えていきます。

- 戦闘履歴
- ランキング履歴
- メッセージ
- ログイン履歴
- アイテム取得履歴
- エラーログ

最初は小さく見えても、ユーザー数やプレイ回数が増えると、想像以上にデータが増える可能性があります。

そのため、本番公開する場合は、以下を事前に決めておくと安心です。

- どのタイミングでProプランへ移行するか
- 不要な履歴データをどのくらい保持するか
- バックアップをどのように取るか
- 誤更新時にどのように戻すか
- 無料枠の上限に近づいたとき、どこで気づけるようにするか

:::message
無料枠は「開発・検証・小規模公開」には便利ですが、マネタイズや長期運用を前提にするなら、早めに有料プランへの移行条件を決めておく方が安全だと感じています。
:::

## Domain / DNS：Cloudflare

ドメインとDNSはCloudflareで管理する想定です。

Cloudflare Pagesとの相性がよく、DNS管理もまとめやすいからです。

個人開発では、最初から大きな構成にするより、管理するサービスをできるだけ減らす方が運用しやすいと感じています。

## この構成のメリット

この構成のメリットは、個人開発としてバランスがよいことです。

- フロントエンド配信が軽い
- APIサーバーを分離できる
- DBとAuthを自前で作り込まなくてよい
- 小規模から始められる
- 将来的に拡張しやすい

特に、フロントエンド、バックエンド、DB / Authの役割が分かれているため、問題が起きたときに切り分けやすいです。

## 気をつけたい点

一方で、注意点もあります。

### サービスが分かれる

Cloudflare Pages、Render、Supabaseを使うため、複数サービスをまたいだ構成になります。

そのため、以下のような設定は少し複雑になります。

- 環境変数
- CORS
- 認証情報
- デプロイ設定
- 障害時の切り分け

個人開発では、構成を増やしすぎると管理が大変になります。

便利なサービスを使いつつも、「自分が運用できる範囲」に収めることが大事です。

### バックエンドの負荷

Webブラウザゲームでは、待機時間や更新頻度によってバックエンド負荷が変わります。

例えば、以下のような機能は負荷が増えやすいです。

- バトルを連打できる
- ランキングを頻繁に更新する
- チャットをリアルタイムにする
- ユーザー間取引を入れる

特にチャットやリアルタイム機能は便利ですが、個人開発では運用負荷が高くなりやすいと感じています。

最初から全部入れるより、非同期処理や簡易的な仕組みから始める方が安全です。

### DB変更が怖い

ゲームではユーザーデータが資産になります。

そのため、DBの変更は、内容を理解した上で、細心の注意を払って更新する必要があります。

例えば、以下のような事故が起きると、信頼を大きく失います。

- 所持アイテムが消える
- 所持キャラクターが消える
- 課金状態が壊れる
- ランキングが不整合になる

:::message alert
AIエージェントを使った開発では、DB変更や削除処理を任せきりにしない方が安全です。  
特に本番データに影響する変更は、必ず人間側で内容を確認する必要があります。
Migrationファイルを必ず自分でレビューするなど、人間側の運用方針もしっかりと考えていきましょう。
:::

DB変更や削除処理は慎重に扱う必要があります。

## 最初から入れすぎない

個人開発では、最初から大きな構成にしすぎない方がよいと感じています。

例えば、最初から以下を全部入れると大変です。

- リアルタイムチャット
- ユーザー間取引
- ギルド
- 通知
- 複雑なランキング
- 課金アイテム管理
- 管理画面

どれも魅力的ですが、運用コストが上がります。

最初は、以下くらいに絞る方が、リリースまで到達しやすいと思います。

- ログイン
- 基本プレイ
- データ保存
- ランキング
- 最小限の管理機能

## 待機時間も設計の一部

ブラウザゲームでは、待機時間も技術構成に関係します。

例えば、バトルを何秒に1回できるかで、APIへのリクエスト数が変わります。

待機時間が短いほど、以下のような問題が出ます。

- サーバー負荷が増える
- DB更新が増える
- 不正対策が難しくなる
- 課金短縮とのバランスが難しくなる

そのため、ゲームテンポだけでなく、運用コストの観点でも待機時間を考える必要があります。

## ランニングコストについて

個人開発では、月額費用をどこまで許容するかも重要です。

執筆時点では、以下のような費用感を想定しています。

| 領域 | 使用サービス | 想定プラン | 月額目安 |
| --- | --- | --- | --- |
| フロントエンド | Cloudflare Pages | Free | $0 |
| バックエンド | Render | 有料インスタンス | 約$7〜 |
| DB / Auth | Supabase | Pro | $25〜 |
| Domain / DNS | Cloudflare | ドメイン費用のみ | ドメインにより変動 |

合計すると、最低限の本番運用でも月額30ドル台から40ドル台程度は見ておいた方がよさそうです。

もちろん、無料枠だけで始めることもできます。  
ただし、ブラウザゲームとして継続的に遊んでもらうことを考えると、無料枠には以下のような制約があります。

- バックエンドのCold Start
- Supabaseプロジェクトの一時停止
- DB容量や転送量の上限
- サービスごとの無料枠制限
- 将来的な従量課金
- 障害時の調査や復旧のしやすさ

:::message
最初は無料枠で検証し、本番公開やマネタイズを考える段階で有料プランへ移行する、という進め方が現実的だと感じています。
:::

個人開発では、数千円の固定費でも長期的には無視できません。

月額コストを下げることも大事ですが、それ以上に「運用中に詰まらない構成か」を考える必要があります。

## 技術構成を考えるときの基準

個人開発では、「何が一番高性能か」よりも「運用できるか」が大事だと思います。

自分の場合は、以下を基準にしています。

- 月額コストが重すぎない
- デプロイが簡単
- 障害時に原因を追いやすい
- DBと認証を自前で抱えすぎない
- 将来的に拡張できる
- AIに実装を任せても壊れにくい

特に最後の「AIに実装を任せても壊れにくい」は、最近かなり重要だと感じています。

AIは実装速度を上げてくれますが、構成が複雑すぎると、変更範囲が広がりやすくなります。

## まとめ

個人開発ブラウザゲームでは、技術構成をシンプルに保つことが大事です。

現在は、以下の構成を想定しています。

| 領域 | 使用サービス | 主な役割 |
| --- | --- | --- |
| フロントエンド | Cloudflare Pages | フロントエンド配信 |
| バックエンド | Render | バックエンドAPI |
| DB / Auth | Supabase | データベース・認証 |
| Domain / DNS | Cloudflare | ドメイン・DNS管理 |

この構成は、小規模に始めつつ、必要に応じて拡張しやすいバランスだと感じています。

ただし、チャット、ユーザー間取引、リアルタイム機能、課金管理などを入れると、運用負荷は一気に上がります。

また、無料枠は開発初期には便利ですが、本番運用では停止・容量・復旧面のリスクがあります。

まずは小さく作り、データを壊さず、運用できる範囲で広げていくのがよさそうです。
