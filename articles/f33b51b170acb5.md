AIによるコード生成が日常化した今、エンジニアの役割は「コードを書くこと」だけではなく、「生成されたコードをどう確認し、どう受け入れるか」にも広がっています。

本記事では、Codex（GPT-5.5）とClaude Code（Ops4.6 / Sonnet4.6）を併用する中で感じた、AI時代のコードレビューの考え方について、備忘録として記載します。

特に、GitHubのPull Requestをレビューする場面を想定し、概念的な話だけではなく、実際にどこを見るべきかを中心に整理します。

## AIがコードを大量に生成する時代

CodexやClaude Codeのようなツールを使うと、コードの生成速度は大きく上がります。

数分で数百行、場合によっては1,000行以上の変更が作られることもあります。

一方で、その変更を人間が従来どおり1行ずつ確認しようとすると、レビュー側の負荷が急激に高くなります。

「AIが短時間で作った大量の差分を、人間が長時間かけて精査する」という構造は、あまり持続可能ではありません。

そのため、AI時代のコードレビューでは、レビューの観点を少し変える必要があると感じています。

AIが書いたコードを人間がすべて目視で保証するのではなく、人間が確認すべきこと、CIやテストに任せること、AIに説明させることを分ける必要があります。

ここで重要になる考え方の一つが、ハーネスエンジニアリングです。

## ハーネスエンジニアリングという考え方

AIにコードを書かせる場合、重要なのは「AIにうまく書かせること」だけではありません。

AIが出した変更を安全に受け入れるための仕組みを、あらかじめ用意しておくことが重要です。

なお、ハーネスエンジニアリングは本来、AIエージェントが作業しやすく、かつ安全に検証できる環境全体を設計する考え方だと理解しています。
本記事では、その中でもGitHubのPull Requestレビューに関係する部分に絞って扱います。

ハーネスとは、もともと「制御する」「支える」「安全につなぎ止める」といった意味を持つ言葉です。ソフトウェア開発においては、テストハーネスのように、対象のコードを安全に実行・検証するための枠組みとして使われます。

AI時代の開発では、この考え方をもう少し広げて捉えると良いと感じています。

```md
- AIが変更してよい範囲をIssueで明確にする
- PRサイズを小さく保つ
- TypeScript、ESLint、Prettier、test、buildをCIで自動実行する
- 変更内容をAIに自己レビューさせる
- 未確認のリスクをPR上に明示させる
- マージ前に人間が判断すべき観点を固定する
```

つまり、AIに自由にコードを書かせるのではなく、AIの出力を安全に扱うためのレールを作るということです。

人間がすべての行を目視で確認する前提ではなく、機械的に落とせるものは機械で落とし、人間は目的・責務・影響範囲・リスクを見る。

このような構造を作っておくことで、AI生成コードのレビューはかなり現実的になります。

## CodexとClaude Codeの使い分け

私の場合、CodexとClaude Codeは次のように使い分けています。

```md
- Codex: 既存コードの文脈に沿った修正、局所的な実装、軽微なリファクタリング
- Claude Code: 複数ファイルにまたがる修正、設計変更、Issue単位の実装
```

Codexは、既存のコードに近い粒度で修正を進める用途に向いていると感じています。

一方でClaude Codeは、Issueの内容をもとに複数ファイルを横断して変更するような作業に向いています。

ただし、どちらを使う場合でも、最終的にはPull Requestとして差分が出てきます。

そのため、レビューでは「どのAIツールが書いたか」よりも、次のような観点で見ることが重要になります。

```md
- Issueの目的に対して、変更範囲が広がりすぎていないか
- 既存の設計や命名に沿っているか
- 不要なリファクタリングが混ざっていないか
- テストや型チェックで検知できる範囲が確保されているか
- 将来の変更時に、修正しづらい構造になっていないか
```

ツールごとの得意不得意はあります。

しかし、受け入れ判断の軸は、あくまでPRの目的、差分、影響範囲、検証可能性に置く必要があります。

## AIが書いたコードのレビューで見るべきポイント

AIが生成したコードをレビューするとき、私は最初から細かい行単位の確認には入りません。

まず、Pull Request全体を見て、変更の目的と差分の大きさが釣り合っているかを確認します。

### 1. Issueの目的と差分が一致しているか

最初に見るのは、PRが元のIssueに対して過不足なく対応しているかです。

AIは、依頼された作業に関連しそうな修正を広げてしまうことがあります。

例えば、UIの文言修正を依頼しただけなのに、コンポーネントの構造変更やスタイルの大幅な整理まで含まれていることがあります。

この場合、変更内容そのものが悪いとは限りません。

ただし、レビューしづらくなるため、PRとしては分けた方がよい場合があります。

コードレビューで人間がチェックするポイントは次のようなものです。

```md
- Issueに書かれていない変更が入っていないか
- ついでの修正が混ざっていないか
- 本来別PRに分けるべき変更が含まれていないか
- 差分量がレビュー可能な範囲に収まっているか
```

AIに実装を任せるほど、この確認は重要になります。

### 2. 変更範囲が広がりすぎていないか

AIは、局所的な修正のつもりでも、周辺コードをまとめて整理することがあります。

たとえば、次のような変更です。

```md
- 関数名や変数名を広範囲に変更する
- 既存コンポーネントを分割する
- 型定義を作り直す
- 既存の処理フローを別の書き方に変える
```

これらは、単体で見れば改善に見えることもあります。

しかし、目的が小さいPRで大きな構造変更が入ると、レビューの難易度が上がります。

特にGitHubのPRレビューでは、差分が大きくなるほど、次のような問題が起きやすくなります。

```md
- どこが本質的な変更なのか分かりづらい
- レビュー漏れが発生しやすい
- 不具合が出たときに原因を戻しづらい
- マージ後の影響範囲を追いづらい
```

そのため、AIが作ったPRでは、まず「このPRでやるべき変更だけに収まっているか」を確認します。

必要であれば、レビューコメントで次のように返します。

```text
このPRではIssueの対応に絞りたいので、構造整理は別PRに分けたいです。
今回必要な差分だけに戻してください。
```

AIに対しても、人間に対しても、PRのスコープを明確にすることが大事です。

### 3. 保守性、更新性、拡張性が担保されているか

AIは「一見動くコード」を作るのが得意です。

しかし、長期的に見たときに保守しやすいかどうかは、別の観点です。

レビューでは、動作確認だけではなく、次のような点を見ます。

```md
- 既存の責務分離を崩していないか
- 1つの関数やコンポーネントに処理が集まりすぎていないか
- 特定の画面や仕様に依存しすぎていないか
- 将来の変更時に影響範囲が広がりすぎないか
- エラー時の挙動が考慮されているか
```

特にAI生成コードでは、正常系だけがきれいに実装され、異常系や境界条件が薄いことがあります。

たとえば、APIレスポンスが空の場合、権限がない場合、通信に失敗した場合などです。

Pull Requestでは、正常に動くかだけではなく、「失敗したときにどう振る舞うか」も確認する必要があります。

### 4. テスト・型チェック・Lintをハーネスとして用意する

AIが生成したコードをすべて人間が目視で確認しようとすると、現実的ではない量のコードの確認が必要になったり、自分の知識だけでは判断しづらい領域のレビューが難しくなるケースもあります。

そのため、レビュー前に機械的に確認できるものは、できるだけCIに寄せるように設計することが望まれます。

最低限、下記のようなチェックは、PR上で自動実行される状態にしておきたいです。

```md
- TypeScriptの型チェック
- ESLint
- Prettier
- unit test
- build
- 必要に応じたE2Eテスト
```

これらは単なる品質チェックではなく、AIが生成したコードを受け入れるためのハーネスでもあります。

ハーネスが弱い状態でAIに大きな変更を任せると、人間のレビュー負荷が一気に上がります。

逆に、型チェック、Lint、テスト、buildがCIで落ちる状態になっていれば、人間は設計・責務・影響範囲に集中しやすくなります。

AIにコードを書かせる場合は、AIにテストもセットで作らせるとレビューしやすくなります。

例えば、実装依頼時に次のように指示します。

```text
実装だけでなく、変更内容を検証するテストも追加してください。
既存のテストがある場合は、その方針に合わせてください。
```

また、PR作成後には、AIに次のような観点で自己レビューさせることもあります。

```text
このPRについて、レビュー観点を整理してください。
特に、変更範囲、影響範囲、テストで担保できていること、未確認のリスクを分けて説明してください。
```

これにより、人間はPR全体の確認に入りやすくなります。

### 5. AIに「なぜその実装にしたのか」を説明させる

AIが書いたコードをレビューするとき、コードそのものだけを見ると意図が分かりにくいことがあります。

そのため、私はAIに次のような説明を求めることがあります。

```text
今回の実装方針を説明してください。
他に考えられる実装案があれば、それぞれのメリット・デメリットも整理してください。
```

重要なのは、AIが出した実装をそのまま受け入れるのではなく、「なぜその形になったのか」を確認することです。

特に、次のような変更では説明を求めた方が安全です。

```md
- データ構造を変更している
- DBやAPIの仕様に影響する
- 認証・権限に関わる
- 共通コンポーネントを変更している
- 既存の責務分離を変えている
- パフォーマンスに影響しそうな処理を追加している
```

説明を読んだうえで納得できなければ、そのPRはまだマージしない方がよいです。
AIの説明も常に正しいとは限りません。

ただし、説明を出させることで、少なくとも「AIが何を前提に変更したのか」を確認しやすくなります。

### 6. PRサイズを小さく保つ

AI時代のコードレビューで特に大事なのは、PRサイズを小さく保つことです。

AIは一度に多くの変更を出せます。
しかし、人間が安全にレビューできる量には限界があります。

そのため、AIに作業を依頼するときは、最初から次のような制約を入れると安定します。

```text
1PRで完結する範囲にしてください。
不要なリファクタリングは行わないでください。
変更ファイル数が多くなる場合は、実装前に分割案を提示してください。
```

PRが大きくなりすぎた場合は、無理にレビューせず、分割を依頼します。

```text
このPRは変更範囲が広いため、レビューしやすい単位に分割してください。
まずはIssueの目的に直接関係する変更だけを残してください。
```

AIを使うほど、実装速度よりもレビュー可能性を優先した方が、結果的に安全です。

### 7. 人間は「問い」と「制約」に責任を持つ

AI時代のコードレビューでは、人間がすべての行を完璧に理解することは難しくなります。

しかし、人間の責任がなくなるわけではありません。
むしろ、人間が責任を持つべき範囲は明確になります。

それは、AIに何を依頼するか、どの制約を守らせるか、どの条件を満たせばマージ可能とするかです。

たとえば、PRレビューでは次のような問いを持つ必要があります。

```md
- この変更は本当に必要か
- Issueの目的から外れていないか
- 今回のPRで扱うべき範囲か
- 将来の変更を難しくしていないか
- テストやCIで最低限の安全性を確認できているか
- マージ後に問題が出た場合、戻しやすいか
```

AIがコードを書く時代でも、最終的な判断は人間が行います。

その判断を支えるためには、AIに自由に実装させるのではなく、最初に制約を与え、PR上で確認できる形にすることが重要です。

#### AIエージェントへの実装依頼時に入れる制約の例

AIへ実装を依頼するときに入れる制約の例を記載します。

```md
以下のIssueを対応してください。

制約:
- Issueに書かれている範囲だけを対応してください
- 不要なリファクタリングは行わないでください
- 変更ファイル数が多くなる場合は、実装前に分割案を提示してください
- 既存の命名、責務分離、設計方針に合わせてください
- TypeScriptの型チェック、Lint、test、buildが通る状態にしてください
- 変更内容を検証するテストを追加してください
- PR本文には、変更内容、影響範囲、テスト結果、未確認リスクを記載してください
```

レビューしやすいPRになるように、実装前の依頼文や、AIエージェントに常時参照させるルールとして、制約を入れておきます。

AIに対する指示は、単なる作業依頼ではなく、レビュー可能な成果物を作るためのハーネスでもあります。

## まとめ

CodexやClaude Codeを使うことで、実装速度は大きく上がります。

一方で、生成されたコードをそのまま受け入れると、レビューコストや保守リスクが後から大きくなる可能性があります。

人間がコードレビューを実施するにあたっては、次のような観点を重視していくと良さそうに感じます。

```md
- Issueの目的と差分が一致しているか
- PRの変更範囲が広がりすぎていないか
- 既存設計や責務分離を崩していないか
- 異常系や境界条件が考慮されているか
- テスト・型チェック・Lintで担保できているか
- マージ後に戻しやすい変更になっているか
```

AIにコードを任せる部分が大きくなるにつれて、人間は「何を作るか」「どこまでを許容するか」「何をもって安全と判断するか」を明確にする必要があります。

AIの出力を人間の目視だけで受け止めるのではなく、
CI、テスト、型、Lint、PRサイズ、Issueの制約といったハーネスを整えることが重要です。

AIとのコードレビューでは、コードの細部を見る力に加えて、
PR全体の目的・範囲・影響を判断する力がより重要になると感じています。
