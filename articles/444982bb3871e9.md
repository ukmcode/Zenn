「自分はちゃんと言ったのに、相手にうまく伝わらない」

上記のようなケースにおいて、
必ずしも、説明量や知識量が問題ではありません。
このようなケースにおいては、情報設計の問題であることが多いです。

相手への情報の伝達は「正しいことを言う」だけでは成立しません。

- 相手が理解しやすいよう、前提の話をする
- 相手が理解できる順番で話す
- 相手が理解できる粒度で話す

など、会話の組み立て方を設計する力が求められます。

本記事では、
人に考えを伝えるための情報設計について、
普段、自分が意識していることを備忘録として記載しました。

## 認知負荷について考える

相手に説明が伝わらないときに、
「自身の情報不足」や「相手の理解不足」を疑うことがあります。

しかし、上記を満たしていても、相手に物事が伝わらないケースがあります。

例えば、

- 情報が多すぎる
- 説明の順番が時系列になっていない
- 前提が飛躍している

などです。

:::message
自分自身の認知や知識について、
相手も当然知っている前提として会話をすると、
この手の齟齬が起きやすい。
:::

## 相手に考えを伝える時は、文章より構造を意識する

「長文でも伝わる文章」と、
「短いのに伝わらない文章」があります。

人は実際には、
文章を逐語的に読んでいるわけではありません。

- これは何の話か
- どこが重要か
- 何と何が関係しているか
- 結論は何か

こうした構造を、頭の中で組み立てながら読んでいます。

つまり、情報設計とは、

> 相手の頭の中に構造を再現する作業

です。

## 抽象と具体を意識した情報の設計

相手との会話において、抽象的な内容だけでは、
意図を伝えたり理解を得たりすることは困難です。

しかし、具体だけの説明でも、伝わりづらいケースがあります。

例えば、
レビューで「責務分離が必要」と説明したい場合、
単純に抽象論だけを話しても、相手は納得しづらいことがあります。

例えば、

```
- UserServiceという機能がある
- UserServiceは認証・メール送信・プロフィール更新という責務を持っている。
- 責務を分離する必要がある
```

上記のような課題を抱えているケースにおいて、

```
UserServiceは責務が多いので、分離をしたほうが良いです。
```

上記のような抽象的なコメントの場合、
責務を分けた方が良いという意向は伝わっても、

- 何が問題なのか
- 何を改善したいのか

が見えません。

逆に、具体だけのコメントも、局所最適になります。

```
UserServiceが2500行あって、
ユーザー登録、認証、メール送信、
プロフィール更新、権限変更まで全部入っています。
分離をしたほうが良いです。
```

上記のような記載の場合、前提を知っている開発者などであれば、理解できるかもしれません。
しかし、非開発者であるステークホルダーなどが会話相手の場合は、なかなか問題の本質までは伝わらないケースがあります。

そこで、

抽象と具体のバランスを見直した文書設計とします。

```
現在の UserService は、
認証・メール送信・プロフィール更新など、
複数の責務を持っています。

その結果、

- 修正影響範囲が広い
- テストが複雑になる
- 他機能の変更が混ざりやすい

状態になっています。

つまり、
「機能追加の問題」ではなく、
「責務が集中しすぎている問題」です。

そのため、
認証・通知・プロフィール管理を分離して、
責務単位で整理したいです。
```

抽象と具体を整理しながら説明することで、
相手が理解しやすい文章を組み立てやすくなります。

:::message
例示の整理後の文章が、却って冗長だったり、わかりづらいケースもあるかと思います。
文章設計においては、受け手の前提知識や背景も重要となるため、会話の相手や状況に応じた、会話の設計を意識する必要があります。
また、全体に周知すべき内容か、個人間で会話する内容かなど、会話を伝える相手の人数によっても、伝え方は変わってきます。
:::

## おわりに

「情報設計」を通して「相手に伝えること」とは、
自分の知っている情報をそのまま伝えることではなく、
相手の理解につながる文章を設計することです。

「自分が何を伝えたいか」だけではなく、

- どの順番で
- どの粒度で
- どの前提から
- どう認知させるか

を設計すると、伝わり方はかなり変わると思います。
